# PDF statement

## Scope and data ownership

The Desktop Reports export is generated by the Rust storage engine through
`report_generate` and `report_export_pdf` in
`rust/ledgera_engine/storage/src/reporting.rs`. Rust owns report arithmetic,
historical operation-time values, current-rate conversion, filtering, sorting,
transfer integrity checks, and export serialization. Kotlin only supplies
`ReportFilters` and presents export progress. The legacy Python exporter remains
available for the Python application and is kept semantically compatible; it is
not used by the Kotlin Desktop export path.

The report result contains fixed values and current equivalents side by side.
Fixed values use the values stored on records and transfers. Current values are
resolved by the SQLite-backed currency service only when `totals_mode` is
`current`. A PDF export must never recalculate historical values.

## Export parameters and boundary

The public Kotlin/UniFFI boundary is:

- `ReportFiltersDto`: wallet, period, category, tag, tag mode, totals mode, and
  category grouping;
- `ReportResultDto`: summary, operations, logical transfers, monthly/category/tag
  summaries, and debts;
- `ReportExportResultDto`: exported row count and target path.

These signatures remain stable. The PDF renderer consumes the same result as CSV
and XLSX and therefore inherits the same filters, ordering, fixed/current mode,
and wallet-specific transfer semantics.

## PDF pipeline

`report_export_pdf` builds a small stream of typed sections and sends it to the
Rust `printpdf` backend. The renderer uses A4 landscape dimensions, 12 mm page
margins, a bundled Unicode font, measured wrapping, repeated table headers, and
page headers/footers. Rows are kept intact across page boundaries. The section
order is Overview, Operations, Transfers, Monthly, Categories, Tags, and Debts;
empty sections are omitted or represented by a localized empty-state row.

The renderer uses centralized presentation tokens for typography, spacing,
fills, borders, and text colors. Financial arithmetic is deliberately outside
the renderer. Adding a new section requires adding its data rows, column widths,
and a section header to the PDF section builder; it must not query SQLite or
perform a second calculation.

## Formatting and localization

PDF labels currently follow the stable export contract used by Rust Desktop.
Amounts are formatted for presentation only: grouped thousands use U+202F,
positive values use `+`, negative values use U+2212, and zero has no sign. Date
values use `DD.MM.YYYY` where a localized date formatter is available; ISO dates
remain accepted at the API boundary. The rate mode is shown explicitly as a
`Fixed` or `Current` chip/note.

The bundled font must contain Cyrillic, U+20B8 (tenge sign), U+2212, middle dot,
em dash, and ellipsis. If the tenge glyph is unavailable, the formatter uses
`KZT` as a safe fallback rather than emitting a missing-glyph box.

## Compatibility rules

- Existing report calculations, filters, ordering, and transfer invariants are
  unchanged.
- Transfer legs remain out of ordinary income/expense rows.
- A logical transfer is rendered once with both wallets, amounts, currencies,
  historical rate, commission, current/fixed base equivalents, and integrity
  status.
- Malformed transfers remain visible with an error status and do not contribute
  unverified values to totals.
- The PDF is searchable/selectable and carries title, author, subject, and
  language metadata where supported by the backend.

## Verification

Rust tests cover formatting, fixed/current invariants, transfer rendering,
landscape page dimensions, metadata, Unicode text, and multi-page output. The
Kotlin Desktop smoke test verifies that the existing export action reaches the
Rust PDF path without changing the engine or report ViewModel lifecycle.
